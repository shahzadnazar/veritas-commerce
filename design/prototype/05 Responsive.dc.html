Phase 5 of 6

Three widths, one system.

Nothing here is a shrunken desktop screen. Each layout is re-composed for what the person is doing at that width: customers browse and buy one-handed, sellers triage orders between packing, admins review queues at a desk.

Mobile · < 600

One column, tab bar, sticky action bar, tables become cards, filters become a sheet.

Tablet · 600–1199

Two columns, icon-only sidebar, tables keep their three most decision-relevant columns.

Desktop · ≥ 1200

Full layouts as designed in Phases 2–4. 240px sidebar, full tables, side panels.

Rules that hold at every width
  • Touch targets never below 44px.
  • Body text never below 14px; table text never below 13px.
  • The primary action stays visible without scrolling — sticky bar on mobile.
  • No horizontal scrolling except inside a table that explicitly opts in.
  • Nothing is removed on mobile that the person needs to complete the task; it moves.
  • 2px section rules and 0px radius hold everywhere.

Dev note — customer mobile
The product page's buy bar is position:sticky;bottom:0 and always shows the live total — it is the one element that must never require scrolling. Dev note — seller mobile
The order card is the same data as the desktop row, filtered to four fields plus one action — it is a different component, not a responsive table hack. The long Add Product form splits into four steps with a persistent draft, so a seller can start a listing on a phone and finish it on a desktop. Status filters scroll horizontally; that is the one place horizontal scroll is allowed.

Dev note — admin mobile
Two admin surfaces are mobile-complete: the dashboard and the decision queues (applications, product review, payouts), because those are time-sensitive. Everything else degrades to the same explicit fallback — headline figures, a CSV escape hatch, and a clear sentence about why. Required-reason dialogs become bottom sheets so the keyboard doesn't push the buttons off-screen.
