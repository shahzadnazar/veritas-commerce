The MarketHub design system

One visual system for three audiences — a customer storefront, a seller operating portal and an admin control centre. Everything below is the shared vocabulary: tokens, components and states that every screen in Phases 2–4 is assembled from.

Customer

Generous space, large imagery, one action per view. Trust before density.

Seller

Persistent sidebar, tables over cards, status legible at a glance.

Admin

Highest density. Every row is reviewable, every action is auditable.

Assumptions
  • General-goods marketplace, USD, US shipping.
  • Scope is exactly the Phase 1 spec — no reviews, wishlists, coupons or time-series charts.
  • Product imagery is drop-in slots; photography renders grayscale per the system.
  • Commission is a snapshot on each order and never re-computed.
  • Prototype carries real state — cart, forms and statuses persist across screens.

Dev note — status color
Only four semantic fills exist. Never introduce green/amber/blue: the system is mono, so status is carried by fill weight and label, not hue. Map every backend status enum to one of these four in a single shared statusTone() helper so storefront, seller and admin can never drift.

Rules
  • Everything is flush left. No centred headings, no centred button labels.
  • All money and quantity figures use font-variant-numeric: tabular-nums so columns align.
  • Storefront body is 15px; seller and admin tables drop to 14px — the only density difference between the three apps.
  • Never below 12px, and never below 14px for anything tappable.
Dev note
Type scale is fixed and comes from the stylesheet's h1–h6 plus four utility sizes. Do not add intermediate sizes per screen — if something needs to feel bigger, change its weight or the space around it.

Commission snapshot
Every completed order stores its own order total, commission amount, seller earning and the rate that produced them. Changing the platform rate never alters a historical order — the UI always shows the rate from the order, labelled with its date.

13b

Loading states for tables and forms

Added from the Phase 6 review — finding 2

Every route with a known shape gets a skeleton that mirrors it. Two more are needed beyond the product grid: the data table and the submitting form.

Table skeleton — real column widths, 8 rows
Column widths and row height match the real table exactly, so nothing shifts on load. Only the first column shimmers — a full grid of moving bars reads as noise. Shown after 200ms; faster responses skip it entirely.
Form — submitting
Fields drop to 45% and lock, the primary button holds its width and swaps to the present participle. Never a full-page overlay — the person keeps their context.
Dev note — one status helper
Phase 6 finding 1: every badge in all three apps must read its tone from a single statusTone(status) returning one of four values — neutral, pending, critical, inactive. No per-screen lookup tables. A test should assert every status enum in the API has a mapping.
Design system complete, including the two additions from the Phase 6 review. Every screen in Phases 2–5 is assembled from the components above.
