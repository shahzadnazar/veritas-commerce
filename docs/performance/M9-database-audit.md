# M9 — database index and query-plan audit

Every read surface in the application was run against a launch-sized
database under `EXPLAIN (ANALYZE, BUFFERS)` and the plans were read. This
records what was found, what was changed, what was deliberately left
alone, and what the measurements do not cover.

The per-surface numbers live in
[`read-surface-plans.md`](read-surface-plans.md), which is generated by
`php artisan veritas:query-plans` and should be regenerated after any
change that could move a plan.

## Method

Three decisions shaped the audit, and each of them was a way of avoiding
a comfortable answer.

**Measured, not estimated.** Every figure is execution — actual rows,
actual milliseconds, actual buffer pages — from `EXPLAIN (ANALYZE,
BUFFERS)`. Planner cost estimates were never used to claim an
improvement. A cost estimate falling is not evidence that anything got
faster; it is evidence that the planner changed its mind.

**At launch scale, with the skew.** Plans were taken against ~857,000
generated rows: 10,000 products, 28,170 offers, 20,000 orders, 53,407
ledger entries, 200,000 interaction events. Size alone would not have
been enough. Uniform data gives the planner flat statistics and
flattering choices, so the generator produces three seller tiers spanning
a 25x catalogue range, a contested band of products carrying twenty
offers against a tail carrying one, and five categories holding a third
of the catalogue. Physical order is a statistic too: offer ids are
assigned in scrambled order, because numbering them by seller would have
handed `offers.seller_account_id` a correlation of 1.0, under which every
index scan on it looks free. See
`app/Support/Performance/PerformanceDataset.php`.

**Through the application's own queries.** The surfaces are the real
query objects invoked the way controllers invoke them, so the
measurements include the count query behind every paginator and the
second statement behind every eager load — the ones nobody writes on
purpose. Hand-written representative SQL would have measured the
benchmark.

`SET enable_seqscan = off` was not used anywhere. A plan produced by
lying to the planner is not a plan production will ever run.

## What was found

### 1. Fuzzy search disabled every search index — HIGH, fixed

`product_search_documents` carries three GIN indexes: one on the
tsvector, one on the identifier array, one on the trigrams of the
normalised title. None of them was being used. Every keyword search was
a sequential scan of the whole document table — and because a search page
issues five statements over the same predicate (results, count, brand
facet, condition facet, in-stock count), that was five full scans per
page of results.

The cause was one clause:

```sql
word_similarity(?, normalised_title) > 0.3
```

A function over a column has to be evaluated per row, so the trigram
index cannot serve it. And because that branch was `OR`'d with the
full-text and identifier branches, its unindexability was contagious:
PostgreSQL cannot combine index scans for an `OR` when one arm needs a
scan anyway, so all three indexes went unused.

`pg_trgm` offers the same test as an operator, `? <% normalised_title`,
which the GIN index implements directly. The operator takes its threshold
from a session setting rather than from the query, so the setting is
applied to every connection from the same constant the old clause used
(`App\Support\Database\ConfigurePostgresSession`).

Measured on the same phrase, same session, same database:

| | Function form | Operator form |
| --- | ---: | ---: |
| Execution time | 25.655 ms | 0.223 ms |
| Buffer pages | 1,434 | 22 |
| Plan | Seq Scan | BitmapOr over all three GIN indexes |

At the surface level, `search: phrase, in stock, cheapest first` went
from 108.06 ms to 12.75 ms across its five statements, and
`search: deep page (page 40)` from 125.91 ms to 21.94 ms.

**`search: free-text phrase` did not improve, and that is correct.** The
phrase it uses matches about 12% of the generated catalogue, and at that
selectivity PostgreSQL is right to prefer a sequential scan over a bitmap
heap scan of a fifth of the table. The long-tail case — the shape of most
real search traffic — is the one the indexes exist for, and it is now
6.57 ms across all five statements against 92–164 pages. See
[Limits](#limits-of-this-audit) on why the popular-term case is worse
here than it will be in production.

The change is a rewrite of the predicate, not of its meaning: the 97
existing search tests, including the misspelling ones, pass unchanged,
and `TrigramThresholdTest` asserts over the data that the operator
selects exactly what the function selected.

### 2. No index on `seller_ledger_entries.payout_request_id` — MEDIUM, fixed

Opening one payout in the admin console ran:

```sql
select public_id, amount_minor, created_at
from seller_ledger_entries
where payout_request_id = ? and type = ?
limit 1
```

with no index on the column at all. That is a sequential scan of the
entire seller ledger — 53,407 rows, 2,486 pages, 5.5 ms here — to find a
single settlement debit, and it grows with the lifetime size of the
ledger rather than with anything about the payout.

Now a partial index, because the column is null on every earning and set
only on payout debits (1,836 rows of 53,407, and a smaller fraction as
earnings accumulate). Every query that reads it is an equality match,
which excludes null anyway.

The payout detail surface went from 7.69 ms to 2.71 ms overall; its
slowest statement from 5.30 ms to 0.82 ms, and from 2,486 buffer pages to
180.

### 3. The seller inventory list scanned every seller's stock — MEDIUM, fixed

The seller inventory page sorts by `inventory_balances.available`. No
index can order that, so the planner had to materialise the matching rows
anyway — and having decided that, it chose to hash-join the *whole*
balances table rather than loop over the seller's offers. 28,170 rows
scanned to return 220.

The existing index already led on `(offer_id, available)`. What it could
not do was answer the query without returning to the heap for `on_hand`
and `reserved`, and that heap cost is what made the sequential scan look
cheaper. Carrying those two columns as `INCLUDE` payload turns the join
back into a nested loop over an index-only scan with zero heap fetches:

| | Before | After |
| --- | ---: | ---: |
| Execution time | 3.04 ms | 0.50 ms |
| Buffer pages | 1,366 | 452 |
| Plan | Hash Join over Seq Scan | Nested Loop over Index Only Scan |

The new index replaces the old one rather than joining it. The key
columns are identical, so nothing the old index could serve is lost, and
a second index on a table written on every reservation, sale and restock
would be a real write cost for a read nothing needs.

## What was measured and deliberately not changed

### The admin platform finance summary

Eight statements, four of them full scans of the seller ledger and one of
`platform_revenue_entries`; ~40 ms today and linear in lifetime volume,
because the query is "sum every entry ever, grouped by status" with no
date bound.

A covering index on `(currency, status, type) INCLUDE (amount_minor)` was
built and measured. **PostgreSQL kept the sequential scan** — the whole
index still has to be read for an unbounded aggregate, and at this width
the planner did not think it cheaper. The index was dropped. Adding
storage and write amplification to a hot append-only financial table for
no measured read benefit is exactly the kind of change this audit exists
to prevent.

The real answer is a daily rollup or a bounded date window, which is a
change to what the screen means rather than to how it is indexed. It is
recorded below as a recommendation. It is not a launch blocker: it is one
admin screen, at 40 ms, at Phase-1 volume.

### Sequential scans that are the right answer

Reported by the tool only for relations of at least 5,000 rows, and even
then not every one is a defect:

- `category listing` and `sitemap` scan `product_search_documents`
  returning 5,394–6,013 of 10,000 rows. Reading half a table through an
  index is slower than reading it directly. Correct.
- `moderation: review queue` scans all 5,250 reviews. At that size the
  scan is cheaper than a descent, and the queue is an admin screen.
- The whole-marketplace aggregates above, for the same reason.

No index was added for any of these. A sequential scan is a defect when
the query wants a small fraction of a large table, not whenever it
appears in a plan.

### Six indexes on `interaction_events`

The highest-write-rate table in the system carries 44 MB of indexes
against 28 MB of heap — the worst ratio in the database, and the obvious
candidate for pruning. Each one was traced to a reader before being left
alone:

| Index | Read by |
| --- | --- |
| `(user_id, created_at)` | `RecentlyViewedStrategy`, `PersonalAffinityStrategy` |
| `(anonymous_session_id, created_at)` | the same two, for signed-out visitors; `RebuildProductAssociations` |
| `(event_type, created_at)` | `SearchHealth`, `RebuildMarketplaceMetrics`, `RebuildSearchMetrics` |
| `(product_id, event_type)` | `RebuildProductMetrics`, `RebuildPopularityScores` |
| `event_id` unique | ingestion idempotency — a correctness constraint, not a performance index |
| primary key | — |

The three read surfaces over this table (`search health`,
`recently viewed`, `personal affinity`) are all index-served, between
0.56 ms and 2.04 ms, with no sequential scan. Nothing was dropped.
Local `pg_stat_user_indexes` counts were not used as evidence either way:
on a freshly generated database they say nothing about production.

### Foreign keys without indexes

`payout_settlement_attempts`, `payout_status_history`, `shipment_items`
and the event tables all carry foreign keys, and all of them already have
an index on the column a measured query looks up. No index was added to a
foreign key merely for being one.

## Connections and sessions

Indexes are only half of "the database is ready". The other half is what
happens when a query goes wrong, and PostgreSQL's defaults there are all
zero — meaning wait forever.

| Setting | Was | Web request | Console |
| --- | --- | --- | --- |
| `statement_timeout` | 0 (unbounded) | 15,000 ms | unbounded |
| `lock_timeout` | 0 (unbounded) | 5,000 ms | unbounded |
| `idle_in_transaction_session_timeout` | 0 (unbounded) | 60,000 ms | 60,000 ms |

The failure these prevent is not a slow page; it is an outage. There are
a hundred connections. A statement with no time limit holds one until it
finishes, so a handful of them takes the pool and every other request —
including the healthy ones — queues behind pages nobody is still waiting
for. `lock_timeout` matters for the same reason from the other side: a
statement waiting for a lock puts every later statement on that table
into the same queue, which is how a routine migration takes a site down.

The idle-in-transaction limit is the quiet one. It fires only on a
session doing nothing at all inside an open transaction — which no
legitimate path does for a minute, and a crashed worker does forever,
holding its locks and blocking `VACUUM` the whole time. That is where
table bloat and stuck DDL come from.

Console processes are exempt from the first two on purpose: migrations,
backups and the analytics rebuild are supposed to take minutes, and a
statement timeout that killed a migration halfway through would be the
cure doing the damage. They are not exempt from the third.

All three are configurable, and zero still disables any of them.
`app:production-check` warns when one is unbounded.

### One bug this introduced, and what it taught

The listener that applies these settings originally ran them through
`Connection::statement()`. `ConnectionEstablished` fires when Laravel
*builds* the connection object, which is before its PDO is opened — so
the settings were what opened it, and when opening failed, Laravel's
lost-connection recovery called `reconnect()`, which dispatches
`ConnectionEstablished` again. A single unreachable database recursed
until the kernel killed the process at six gigabytes. The symptom was the
entire test suite dying with no output and no failing test.

It now goes straight at the PDO handle, behind a re-entrancy guard, and
swallows failures — a session that cannot be configured is a connection
that cannot be used, and the next real query reports the real error.
`DatabaseSessionTest::an_unreachable_database_fails_rather_than_recursing`
holds that shut.

## Recommendations, not done here

1. **A search page evaluates the same predicate five times.** Even now
   that all five are index-served, one page of results costs five bitmap
   scans over the same rows. Computing the facets in a single pass — one
   scan feeding several `FILTER` aggregates — would cut it to one. That
   is a query redesign, not an index, and it belongs with the load
   testing that can show what it is worth.
2. **The platform finance summary needs a bound.** Either a date range on
   the screen or a daily rollup table. Linear-in-lifetime aggregates are
   fine until they are not, and the transition is abrupt.
3. **Watch the `product_search_documents` scan threshold.** Category
   listings return 60% of the table today because the generated catalogue
   has 200 categories. A real catalogue has more, the fraction falls, and
   the plan will flip to an index scan on its own. Worth re-measuring
   once real category distribution exists rather than pre-optimising for
   a distribution that is an artefact of the generator.

## Limits of this audit

Stated plainly, because a measurement whose limits are unstated gets
quoted as if it had none.

- **One machine, one run, no concurrency.** Every surface was measured
  alone against a warm buffer cache. Nothing here says how the database
  behaves under a hundred concurrent sessions; that is load testing, and
  it has not been done yet.
- **The generated vocabulary is too small.** Product titles are built
  from eight materials and twelve nouns, so a common word matches ~10% of
  the catalogue where a real one would match a fraction of a percent.
  This makes popular-term search look *worse* than it will be, and makes
  the long-tail case the more representative of the two. It does not
  affect any finding: the fuzzy predicate was unindexable at every
  selectivity.
- **`random_page_cost = 4` on this machine.** That is the default for
  spinning disks and biases the planner *against* index scans. Findings
  taken under it are conservative — a production server on SSD storage
  with `random_page_cost` lowered would use these indexes at least as
  readily, not less.
- **Batch jobs were timed but not planned.** `analytics:rebuild` and
  `recommendations:rebuild` complete in 2.0 s and 0.3 s against this
  dataset; their statements were not put through the plan harness,
  because the harness only explains `SELECT`s and these write.
- **No write-path measurement.** Insert, update and lock behaviour under
  contention is a separate exercise. The index changes here add one
  partial index to a table where the column is usually null, and replace
  one index with a wider version of itself; both were chosen with write
  cost in mind, but neither was measured for it.

## Reproducing this

```bash
# A scratch database. Never the development or PHPUnit one — both are refused.
createdb veritas_perf
DB_DATABASE=veritas_perf php artisan migrate --force
DB_DATABASE=veritas_perf php artisan veritas:seed-performance --scale=phase1 --force

# Plans for every read surface.
DB_DATABASE=veritas_perf php artisan veritas:query-plans --out=docs/performance/read-surface-plans.md

# Statement-by-statement detail for one of them.
DB_DATABASE=veritas_perf php artisan veritas:query-plans --detail="inventory: first page"
```

The seeder empties its target, so it refuses a production-looking
`APP_ENV`, any database named in `VERITAS_PROTECTED_DATABASES`, and the
database `phpunit.xml` names. Every row it writes carries the marker
`0PERF` in its `public_id`, and `app:production-check` fails if a single
marked row is present on a deployment.
